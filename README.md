# Mobile AI Coaching App 🏎️

![Mobile AI Coaching App](/images/mobile-ai-coaching-app.png)

The **Mobile AI Coaching App** is the Android edge component of **ApexAI**. It runs in the car or trackside on an Android device, receives live telemetry from the ApexAI simulator or a CANable USB adapter, maps the car to track sectors, and turns the selected memory bank into concise audio coaching.

The app is built for offline, low-latency driver feedback. It can use a deterministic rules runner for immediate telemetry threshold checks, or a Gemma-powered coach for on-device reasoning over the same memory notes. Both modes use Android `TextToSpeech` for audio delivery and both are driven by the downloaded memory bank JSON generated by the ApexAI dashboard.

## Coach Modes 🧠

The AI Coach screen exposes two coach modes through `CoachType.kt`: `Heuristic-based coach` and `Gemma-based coach`. Both modes receive the same `TelemetryPacket` stream, use the same selected memory bank JSON, map GPS to the same `track_sectors.json` sector data, and return the same `CoachingPayload` shape for the UI and audio system.

### Coach Type 1: HeuristicBaseAICoach ⚡

`HeuristicBaseAICoach.kt` is the deterministic, lowest-latency coach. It does not call an LLM. It treats the memory bank as an executable rule table.

The audio command is triggered only when a memory-bank note for the current sector evaluates to true. For each telemetry packet, the coach finds the closest track sector, loads only that sector's notes, pulls the requested metric from either the live packet or the sector telemetry snapshot, and compares it with the note's `operator` and `threshold`. A note with `metric = "speed"`, `operator = ">"`, and `threshold = 85.0`, for example, triggers when the current speed is above 85.0. A note with `metric = "min_speed"` can trigger from the sector tracker instead of the raw packet.

Initialization:

- `init(selectedMemoryJsonFile)` loads the selected memory bank through `MemoryBank`.
- If the same file is already active, initialization returns early.
- When a new file is selected, it clears spoken-command cooldowns and resets the sector tracker.

Runtime flow:

1. `onTelemetry(packet)` updates `SectorTelemetryTracker`.
2. If GPS or sector mapping is unavailable, it returns `null`.
3. It fetches sector-relevant notes from `MemoryBank.getRelevantNotes(latitude, longitude)`.
4. Each note is evaluated with `packet.metricValue(metric, sectorTelemetry)` and `compareMetric(currentValue, operator, threshold)`.
5. Eligible notes are filtered through a 12-second cooldown keyed by `sector_id` and command.
6. If several notes trigger, it selects the lowest `priority`, then highest `frequency`, then stable `id` order.
7. It speaks `command`, falling back to `description` if `command` is blank.
8. It returns a `CoachingPayload` for the UI.

In short, `HeuristicBaseAICoach` speaks when all of these are true: the packet has valid GPS, the car is close enough to a known sector, at least one memory-bank note in that sector has a metric value available, the metric comparison passes, the note is not inside its 12-second cooldown window, and the selected note has non-empty command text or description text.

This coach is best when the note should fire exactly when a threshold is crossed. It is predictable, cheap to run, and suitable for safety-critical commands where the memory bank already contains the final wording.

### Coach Type 2: GemmaCoach 🤖

`GemmaCoach.kt` is the on-device LLM coach. It uses the same memory bank and the same sector tracker as the heuristic coach, but asks Gemma to choose whether and what to speak after the app has already evaluated the memory-bank rule conditions.

Initialization:

- `init(selectedMemoryJsonFile)` loads the memory bank.
- It initializes `Gemma4Lite` with `Backend.CPU()` and `enableMtp = true`.
- When the memory file changes, it resets sector telemetry state and clears spoken-command cooldowns.

Runtime flow:

1. `onTelemetry(packet)` updates `SectorTelemetryTracker`.
2. It fetches notes for the closest sector from the memory bank with `memoryBank.getRelevantNotes(sectorTelemetry.latitude, sectorTelemetry.longitude)`.
3. It evaluates every memory note locally, producing `EvaluatedMemoryNote` values with the original `CoachingRecommendation`, `currentValue`, and `conditionMet`.
4. If no note condition is true, it returns `null` without calling Gemma.
5. It builds a prompt containing current telemetry, GPS, closest sector, and all evaluated memory annotations from the memory bank.
6. It calls `Gemma4Lite.generateJSON()` with a racing-coach system prompt and expects:

```json
{
  "shouldSpeak": true,
  "command": "Short racing command.",
  "reason": "Brief telemetry reason."
}
```

7. If `shouldSpeak` is false or `command` is blank, it returns `null`.
8. It maps the command back to the matching triggered note when possible, otherwise uses the highest-priority triggered note.
9. It applies the same 12-second sector/command cooldown, speaks the command, and returns a `CoachingPayload`.

Gemma is not used as the raw trigger detector. The Kotlin code first decides which memory-bank conditions are true. Gemma is used as the final reasoning and wording layer: it sees the selected sector notes, live values, thresholds, optimal/average values, existing note commands, and descriptions, then emits one concise audio-friendly instruction.

This coach is best when several notes could apply, when wording needs context from multiple telemetry fields, or when a shorter/smoother equivalent command is safer than reading the memory bank note verbatim. It has higher compute cost and latency than the heuristic coach, so `DashboardScreen.kt` guards it with an `isThinking` flag to avoid overlapping generations.

The mobile module is native Android: Kotlin, Jetpack Compose, Material 3, OkHttp, USB serial support, Gson, LiteRT-LM, and Android TextToSpeech.

## Key Capabilities ✨

- **Two coach types:** switch between `Heuristic-based coach` and `Gemma-based coach` from the AI Coach screen.
- **Memory bank selection:** fetch available `latest.json` memory banks from the ApexAI GCS bucket, download them to app storage, inspect their JSON, and select one for live coaching.
- **Track-sector awareness:** map GPS telemetry to `track_sectors.json`, then evaluate only the notes for the closest sector.
- **Live telemetry ingestion:** consume telemetry either from the ApexAI SSE simulator or from CANable USB/CAN data decoded on device.
- **Audio feedback:** speak one short command at a time through `AudioDeliveryManager`.
- **On-device Gemma inference:** run Gemma through LiteRT-LM from a local model file, with Multi-Token Prediction enabled for the Gemma coach path.
- **Model chat/test surface:** exercise local Gemma backends and structured JSON output from the app.
- **CAN logging:** save raw CAN frames and USB hex chunks into app external files for later validation.

## Setup ⚙️

Open `mobile/` in Android Studio, or build from the command line:

```bash
cd mobile
./gradlew assembleDebug
```

To run the Gemma-based coach, place the LiteRT-LM model on the device:

```bash
adb shell mkdir -p /data/local/tmp/llm/
adb push gemma-4-E2B-it.litertlm /data/local/tmp/llm/gemma-4-E2B-it.litertlm
```

The app expects this default path:

```text
/data/local/tmp/llm/gemma-4-E2B-it.litertlm
```

For the optional NPU chat backend, `DashboardScreen.kt` also references:

```text
/data/local/tmp/llm/gemma3-tensor-g5-npu.litertlm
```

## Running With Simulated Telemetry 📡

Start the ApexAI telemetry server from the repository root:

```bash
uv run apexai-server --input-file dashboard/data/raw/VBOX0148.vbo --autostart --replay-speed 1.0
```

The mobile `TelemetryManager` defaults to the deployed ApexAI SSE endpoint:

```text
https://apexai-812524149286.us-central1.run.app/events/telemetry
```

For local-device testing, update the URL passed to `TelemetryManager.startListening()` or route the Android device/emulator to the local server endpoint:

```text
http://<host>:8000/events/telemetry
```

The AI Coach screen can also start the app's CAN simulator path through **START SIM**, or read a physical CANable adapter through **START USB**.

## Memory Bank Workflow 🧩

The memory bank is the bridge between post-session analysis and real-time coaching. The dashboard exports JSON notes describing what the driver should do in each sector, and the mobile app loads those notes before the coaching session.

1. Open the **Memory Bank** tab.
2. Refresh the available files list. `MemoryBankFileStore` lists objects from `apexai-bucket` and keeps only non-backup files ending in `latest.json`.
3. Choose a memory file and tap **Pull Memory Bank**.
4. The JSON is saved under the app's internal `filesDir/memory_bank/` folder.
5. Open **AI Coach**, choose the downloaded memory bank, choose a coach type, and start the session.

`MemoryBank.kt` accepts these JSON shapes:

```json
[
  {
    "id": "sec_1_entry_speed",
    "sector_id": 1,
    "tag": "entry",
    "title": "Reduce entry speed",
    "description": "You are carrying too much speed into this sector.",
    "metric": "speed",
    "operator": ">",
    "threshold": 85.0,
    "optimal_value": 82.0,
    "average_value": 88.0,
    "frequency": 0.72,
    "audio_file": "",
    "priority": 1,
    "command": "Brake earlier and slow the entry."
  }
]
```

It also supports object wrappers with `coachingRules`, `notes`, or `rules` arrays.

## How The Memory Bank Is Used 🧭

`MemoryBank.kt` loads two things:

- `track_sectors.json` from app assets. Each point has `lat`, `long`, and `segment_id`.
- The selected memory bank JSON from app storage. Notes are parsed into `CoachingRecommendation` objects and grouped by `sector_id`.

For every telemetry packet with valid GPS coordinates, the coach asks the memory bank for relevant notes:

1. The current latitude/longitude is compared to the track-sector points using haversine distance.
2. The nearest sector is accepted only if it is within 80 meters.
3. Only notes for that sector are returned.
4. The coach evaluates each note against live packet metrics or sector-derived metrics.

Supported live packet metrics include speed, rpm, throttle/pedal position, brake pressure, steering, gear, lateral/inline acceleration, yaw rate, oil pressure, fuel pressure, water temperature, engine oil temperature, battery voltage, and fuel level.

Supported sector-derived metrics include:

- `min_speed`: minimum speed observed since entering the sector.
- `coasting_time`: accumulated time with throttle at or below 1 percent and no brake.
- `throttle_start_percent`: how far through the sector the first meaningful throttle application occurred.
- `distance_traveled`: distance covered within the current sector.
- `sector_distance`: total approximated sector length.

## Heuristic vs Gemma Coach 🆚

| Area | Heuristic-based coach | Gemma-based coach |
|---|---|---|
| Core behavior | Direct rule execution | Local rule gating plus LLM selection |
| Inference cost | Minimal | Higher; runs LiteRT-LM on device |
| Trigger source | Memory bank note condition | Memory bank note condition, then Gemma JSON decision |
| Output wording | `command` or `description` from the note | Gemma-generated command, grounded in triggered notes |
| Determinism | High | Lower, but constrained by JSON schema and eligible notes |
| Best use | Fast, exact, threshold-based alerts | Context-aware coaching when multiple telemetry signals matter |
| Cooldown | 12 seconds per sector/command | 12 seconds per sector/command |

## Important Data Contracts 📦

Telemetry arrives as `TelemetryPacket`, which can include GPS, speed, rpm, gear, throttle, brake pressure, steering, acceleration, yaw rate, temperatures, fuel/oil values, wheel speeds, and optional pro sensor channels.

Memory notes are `CoachingRecommendation` records:

- `sector_id` chooses the track sector where the note can apply.
- `metric`, `operator`, and `threshold` define the trigger.
- `optimal_value`, `average_value`, and `frequency` preserve reference-lap context.
- `priority` decides which note wins when multiple notes trigger.
- `command` is the preferred audio instruction.
- `description` is the fallback explanation.

Coach output is a `CoachingPayload` with the instruction, urgency, target sector/corner label, latency field, and optional audio file.

## Notes For Development 🛠️

- `TelemetryManager.kt` consumes SSE telemetry, while `CanableCarDataReader` handles USB/CAN and simulator telemetry. Both feed `TelemetryPacket` into the same coach path in `DashboardScreen.kt`.
- `Gemma4Lite.generateJSON()` strips simple markdown fences before parsing JSON, but the Gemma coach system prompt still requires raw JSON only.
- Cleartext traffic is enabled in `AndroidManifest.xml`, which helps local HTTP simulator testing.
